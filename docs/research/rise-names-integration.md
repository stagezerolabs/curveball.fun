# RISE Names integration research (2026-10-08)

## Verified implementation and live behavior

- Stage0 sells and manages `.rise` names through its [Register](https://stage0.xyz/domains) and [Marketplace](https://stage0.xyz/domains/marketplace) pages. The marketplace offers fixed-price sales and auctions, including reserved short names. Its source is `/Users/macbook/Desktop/projects/stage0/src/pages/DomainsPage.tsx` and `DomainsMarketplacePage.tsx` (notably lines 1329-1338). Curveball can link users to these flows; it does not need to embed Stage0's marketplace.
- Stage0's RNS configuration is **RISE Mainnet only**, chain ID **4153**. Registry `0x6DDca710993C91402d52061868bE76043a4C5888`, resolver `0x36D6383774631565AB0D8F3710748610631A675d`, registrar `0xbCA437a93C2E7396a68Ce49BE224F65eE3CFd6Db`; auction house and marketplace escrow are also configured there. Source: `/Users/macbook/Desktop/projects/stage0/src/config.ts` (`riseMainnet`, `RNS_CONTRACT_ADDRESSES`). Its helper falls back to mainnet addresses for an unknown chain ID, which Curveball must not copy.
- Curveball defaults to **RISE Testnet 11155931** unless `VITE_CHAIN_ID` is set. Source: `src/lib/web3.ts:18`, `src/sdk/curveballSdk.ts:9`. A live request to [Stage0's reverse endpoint](https://api.stage0.xyz/api/public/rns/resolve/address/0x0000000000000000000000000000000000000001?chainId=11155931) returned HTTP 400 `unsupported_chain` with `Only chainId 4153 is indexed right now.` RNS identities therefore need an explicit cross-chain product decision if Curveball remains on testnet.
- Forward name resolution uses Stage0's `GET /api/public/rns/resolve/name/{label}.rise?chainId=4153`, returning registry owner, resolver, resolved address, expiry, and `isExpired`; missing names return 404. Reverse resolution uses `GET /api/public/rns/resolve/address/{address}?chainId=4153`, returning `primaryName`, node, expiry, and source; an address without a primary name returns HTTP 200 with null fields. Source: `/Users/macbook/Desktop/projects/stage0/src/lib/api/rns.ts:529-586`. Stage0's address input accepts direct checksummed EVM addresses and normalizes `.rise` labels, then **refuses expired or unconfigured names** as recipients. Source: `src/lib/hooks/rns/useRnsAddressInput.ts`, `src/lib/rns/address-resolution.ts`, `src/lib/api/rns.ts:615-628` in Stage0.
- Single-name forward reads can also use the **mainnet contracts**: registrar `riseNode()` and `expiryOf(name)`, registry `computeNode(riseNode,labelhash)`, `owner(node)`, `resolver(node)`, and resolver `addr(node)`. Stage0 uses `viem/ens` `labelhash` and `namehash`. Source: Stage0 `src/lib/rns/api.ts:27-227` and `src/lib/rns/utils.ts`. Reverse/primary selection and wallet-wide name discovery **are not solely on-chain reads**: Stage0 uses its Senna API, with a Goldsky fallback for inventory, then verifies registry ownership. Source: `src/lib/hooks/rns/useRnsOwnedLabel.ts` and `src/lib/hooks/rns/useRnsPrimaryName.ts` in Stage0.
- A user selects their public primary name using a wallet signature: `GET /api/rns/primary/authorization`, then signed `POST /api/rns/primary`; Stage0 reads it back from the reverse endpoint. Source: Stage0 `src/lib/api/rns.ts:595-615`, `src/lib/hooks/rns/useRnsPrimaryName.ts`. Do not infer a primary name from the first owned name.
- Live responses from `api.stage0.xyz` to `Origin: https://curveball.fun` and `Origin: http://localhost:3000` returned `Access-Control-Allow-Origin: https://stage0.xyz`, so browser-side `fetch` from Curveball is currently disallowed by CORS. Tested with `curl -i -H 'Origin: ...'` on 2026-10-08. Mainnet reverse endpoint responded 200; testnet responded 400. These are runtime observations, not a published API contract.

## Recommended Curveball scope

Curveball's recorded architecture decision is that the static app uses blockchain/RPC as its sole application data source (`jnote cat curveball.fun ideas`, 2026-10-06). Automatic display of a user's Stage0 **primary** name conflicts with that constraint: Stage0 stores/serves primary selection through Senna, not an on-chain reverse record. Approve a narrow external Stage0 API exception before implementing automatic primary-name display. The existing CORS policy would also have to change; adding a Curveball proxy would reintroduce a hosted API and is inconsistent with the current architecture.

1. First decide whether `.rise` is a **mainnet profile identity displayed in Curveball's testnet UI**, or only appears when Curveball is on mainnet. Mainnet identity across networks is plausible for display, but testnet send/trade recipient semantics must be separately specified. Never query the testnet RNS chain or reuse mainnet contract addresses under testnet chain ID.
2. For an initial integration, show a verified primary `.rise` name beside the connected address with an address fallback and a “Get a .rise name” link to [Stage0 Register](https://stage0.xyz/domains). Link marketplace discovery to [Stage0 Marketplace](https://stage0.xyz/domains/marketplace). If users need to choose/change a primary name, deep-link to Stage0's account/name management rather than reproducing its signed write flow in Curveball.
3. If Curveball accepts `.rise` as a payment/transfer recipient, resolve it on **RISE Mainnet 4153** immediately before submission, require an active expiry and nonzero resolved address, show the exact `0x` destination in confirmation, and pin that address for the transaction. A stored name may later transfer or change its resolver record. For high-value actions, verify the result against mainnet contracts at the latest block, with the Senna API used for discovery and labels.
4. For primary-name display, ask Stage0 to allow Curveball's production and local origins on the public API and confirm API support/rate limits. If that architecture exception is declined, the static/RPC-only alternative is an explicit name entry in Curveball, verified against mainnet registry, resolver, address record, and expiry, with local preference and address fallback. That would be a verified chosen name, **not** Stage0's primary name. A server-side proxy would also work technically but would violate Curveball's current static/RPC-only architecture.

## Planning questions / unverified

- Is the intended first surface only the navbar/profile label, or also creator names, trade history, search, and address inputs? These carry different verification and latency requirements.
- Will Curveball deploy on RISE Mainnet soon? Testnet Curveball plus mainnet RNS needs clear UI text so a `.rise` identity is not mistaken for a testnet registration.
- Does Stage0 offer a supported public integration/API agreement and cross-origin access for Curveball? The endpoints are live and used by Stage0, but no documented stability or rate limit guarantee was found in this review.
- Confirm the desired Stage0 deep link for registration and account management after connecting a wallet; `https://stage0.xyz/domains` and `/domains/marketplace` are live SPA routes, while name-specific deep links were not verified.

## Implemented decision (2026-10-08)

Curveball now permits Stage0's API for the navbar primary-name label. A narrow same-origin rewrite in `vercel.json` and a matching Vite development proxy route `/api/rns/primary/:address` to Stage0's mainnet reverse endpoint. The response is accepted only when it matches the connected address and chain ID, contains an active `.rise` name, and has an unexpired timestamp. The navbar falls back to the shortened address on no name or lookup failure. This is a deliberate external API exception; market and transaction data remain on-chain.
