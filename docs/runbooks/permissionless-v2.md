# Permissionless V2 replacement: local validation and release boundary

This runbook covers the proposed replacement factory and UI. It is a preparation guide, not authorization to deploy. The recorded RISE Testnet V2 factory at `0x36628AbAC7B2cdcde1A8fa21868AfeCB74660ECf` returned `publicLaunchOpen() == false` on October 5, 2026; its existing `openPublicLaunch()` is an owner transaction. The replacement design must allow any wallet to create a token and buy immediately after initialization, without an invitation or a later owner transaction. Keep the existing curve, supply, quote asset, fee splits, creator tax cap, graduation path, and reserve protections unless the reviewed specification explicitly changes them.

## Local validation

1. Test creation and buying from unrelated, uninvited wallets immediately after initialization. Cover both direct `createToken` and atomic launch-and-buy, and prove that an owner cannot close creation later. Test metadata validation, fee snapshots, trades, reserve solvency, graduation, escrow claims, and owner recovery boundaries. Keep the Foundry stateful and fork suites; a passing local unit suite alone does not establish compatibility with Icarus.
2. Run `make -C contracts test`, `make -C contracts test-fork-strict RISE_TESTNET_RPC_URL=https://testnet.riselabs.xyz`, `bun run typecheck`, `bun test`, and `bun run build`. Run `bun run test:integration:sdk` with local Anvil and `bun run test:integration:db` with an isolated `TEST_DATABASE_URL`. Record any skipped fork or database test as unverified. The existing `contracts/scripts/DeployLocal.s.sol` deploys **V1**; it is not a V2 replacement rehearsal. The V2 SDK integration test deploys V2 services to local Anvil.
3. Point the API, indexer, and browser at the same local replacement factory. Use a local Postgres database with V2 migrations and a local `INDEXER_START_BLOCK`/`VITE_DEPLOYMENT_BLOCK` taken from that factory's actual receipt. Confirm `/api/health` reports the intended chain and factory, `/api/config` reports the expected services and fee policy, and a launch appears in `/api/tokens` after finalized-block indexing. Exercise the full UI launch, trade, and market-navigation flow with a fresh wallet. Local database migrations still require the exact approval specified in `AGENTS.md` before execution.
4. On a fresh RISE Testnet fork, validate the replacement bytecode against the current Icarus factory and WETH. Confirm pool creation, post-graduation trading, LP custody, fee claims, and a graduation failure that leaves selling possible. Review bytecode size and security findings again after the final contract diff.

## New deployment record and configuration

The current `deploy-v2-testnet` target refuses a second V2 broadcast when its old receipt exists. The current `record:v2:testnet` flow writes `deployments/11155931/curveball-v2.json`. Do not bypass the guard or overwrite that record. The separate `contracts/scripts/DeployPermissionlessV2.s.sol` supports local chain `31337` with `QUOTE_TOKEN`, `ICARUS_FACTORY`, `TREASURY`, and `DEPLOYER_ADDRESS`, or RISE Testnet `11155931` with pinned dependencies. It requires the declared deployer to equal the treasury before `startBroadcast`, selects that address as the broadcast sender, then verifies the deployed owner, treasury, initialized services, and open launch state. A testnet simulation uses this command, with **no** `--broadcast` flag:

```sh
CONFIRM_PERMISSIONLESS_V2_TESTNET=DEPLOY_PERMISSIONLESS_CURVEBALL_V2_RISE_TESTNET_11155931 TREASURY=0xd07988eCBCf446b9650dC93Ed9c61Bf97F02a8d3 DEPLOYER_ADDRESS=0xd07988eCBCf446b9650dC93Ed9c61Bf97F02a8d3 forge script scripts/DeployPermissionlessV2.s.sol:DeployPermissionlessV2 --rpc-url https://testnet.riselabs.xyz
```

Run it from `contracts/`. A simulation address is not a deployment record. The separate `contracts/scripts/record-permissionless-v2-testnet.ts` is for use only after an approved broadcast; it reads the new Foundry receipt, verifies the live deployment and permissionless state, and refuses to overwrite `deployments/11155931/curveball-v2-permissionless.json`. Run the recorder from the repository root after setting its `CONFIRM_RECORD_PERMISSIONLESS_V2` and `RISE_TESTNET_RPC_URL` variables. Compare that record with finalized chain receipts and verified source. A guarded broadcast command or target still needs to be finalized and reviewed before asking for production approval.

At cutover, the Bun API and indexer need `CONTRACT_VERSION=v2`, `LAUNCHPAD_ADDRESS=<new factory>`, `INDEXER_START_BLOCK=<new deployment block>`, the correct RPC, and `EXPECTED_CHAIN_ID`. The browser build needs matching `VITE_CONTRACT_VERSION=v2`, `VITE_LAUNCHPAD_ADDRESS`, `VITE_DEPLOYMENT_BLOCK`, `VITE_CHAIN_ID`, and `VITE_RPC_URL`. The browser checks the API chain/factory identity; an address mismatch is a failed cutover. The indexer cursor is keyed by chain ID and factory, so the replacement starts a fresh cursor. The Cloudflare Worker adapter currently rejects V2 and cannot be selected as a substitute for the Bun API/indexer.

The browser build also needs `VITE_WALLETCONNECT_PROJECT_ID` to expose RainbowKit QR and mobile wallets. This is a public client identifier. Verify the wallet picker, connection, network switch, and account modal in a real browser before declaring the frontend cutover complete.

Keep the public V1 site and existing testnet V2 record intact until a separately reviewed cutover. A new mainnet release also needs its own chain-specific record and isolated database; the archived `deployments/4153/curveball.json` is not a replacement address.

## Markets reset

The product decision is to list only tokens from the new active factory. Set the API, indexer, and browser to that factory and its actual deployment block together. The current API already filters V2 token rows by configured factory, and the indexer cursor is keyed by factory, so earlier markets remain in the database and on-chain but are absent from the new Markets view. Do not delete old rows or imply that changing the app configuration closes old on-chain markets. New launches use only the replacement factory.

## Production action approval

Finish the code, tests, security review, deployment script, recorded command text, and configuration diff first. Before each deployment/broadcast, on-chain send, database migration, or production infrastructure change, request approval in the exact `AGENTS.md` form: `approve production action: <action-id> — <exact command>`. Approval is bound to that command and the reviewed diff; a changed target or later code change requires renewed approval. Opening the old factory with `openPublicLaunch()` is also an on-chain send and is a separate action from deploying the replacement. This runbook grants no approval for either path.
